# VibeComfy Architecture Notes

This document captures the Phase 0 ready-template architecture after the ContextVar/codegen cleanup and post-F emitter regen. It focuses on generated ready templates, runtime index extraction, manual-template shims, and the `public()` sentinel path.

## 1. Codegen With ContextVar

Generated ready templates now use a ContextVar authoring style:

```python
with new_workflow(READY_METADATA, source_path=__file__) as wf:
    ...
```

`new_workflow()` constructs a `VibeWorkflow` and returns it. `VibeWorkflow.__enter__()` binds the workflow with `vibecomfy.workflow_context.bind_workflow()`, and `__exit__()` resets that token. `templates.node()` accepts either the legacy explicit `wf` form or the ContextVar form. When no explicit workflow is passed, it calls `_current_workflow_or_raise()`, which raises `ContextVarBindingError` with a `next_action` if a template tries to call `node()` outside a workflow context.

The generated code therefore does not need to thread `wf` through every node call. Typed wrappers and the generic `node()` helper consume the active workflow implicitly, create a `_NodeBuilder`, and rely on the builder to expose handles through `.out(...)` or tuple unpacking. This is the central difference from the older local-helper emission style: generated templates are ordinary Python, but their workflow target is scoped by the `with new_workflow(...)` block rather than by generated `nodes[...]` dictionaries or `PUBLIC_INPUTS(**locals())`.

Ready-template wrappers in `vibecomfy.registry.ready_template` follow the same direction. `ready_node()` resolves the active template build context, forwards node creation to the current workflow, and keeps metadata such as source node id, output names, and extra payloads attached to the generated node. That keeps authored template code and generated code on the same execution model.

## 2. Runtime Executor For `template_index.json`

`tools.refresh_template_index` treats the runtime executor as the source of truth for generated ready-template contracts. It walks repository ready-template ids, resolves metadata, and calls `extract_ready_template_contract_runtime()` for each template path.

The runtime extractor imports the template module fresh, calls `build()`, and inspects the resulting `VibeWorkflow`: public inputs from `wf.inputs`, public outputs from `wf.outputs`, requirements, models, custom node packs, artifact expectations, and metadata. If a template cannot be imported or built, the extractor falls back to the AST/static path so manual or temporarily broken templates can still contribute whatever static contract exists.

This split is intentional. Generated templates increasingly use inline `public()` calls, ContextVar-bound wrappers, and runtime registration. Reimplementing all of that in a static AST parser would duplicate the semantics and make byte-identity brittle. The AST extractor remains useful for legacy/manual templates and tooling, but `template_index.json` is refreshed from the runtime shape wherever possible.

Important byte-identity details live in the runtime serializer. Public input rows preserve the current `source` and `status` values, and alias rows must continue to fan out to match the historical index shape. The index contract tests added in Phase 0 pin representative rows after the post-F regen so later refactors have a concrete diff.

## 3. Manual Shims And `SymbolicRefProtocol`

The 23 manual/broken-regen templates are not regenerated by the codemod. Many of them use small symbolic reference objects instead of direct generated handles because their source workflows still need Phase 1 emitter work. Those objects are intentionally duck-typed: they expose a human-readable `.label` and a `.resolve(namespace, wf)` method that returns the concrete node id at runtime.

Phase 0 formalized that duck type as `SymbolicRefProtocol` in `vibecomfy.workflow`. The protocol is runtime-checkable and requires:

```python
label: str
def resolve(self, namespace, wf) -> Any: ...
```

The consumption sites are in `vibecomfy.templates`, not in the static contract layer. `InputSpec.resolve_node_id()` and `_resolve_output_node()` both recognize `SymbolicRefProtocol` before falling back to older compatibility behavior. That makes a desynchronized manual shim fail loudly at the point where a public input or output is resolved, instead of silently producing an incorrect index row or output binding.

The invariant for this sprint is narrow: manual shims may still be broken for regeneration, but they must import, build, and finalize metadata at runtime. The load sweep pins that invariant across all 64 ready templates.

## 4. `public()` And Pending Public Inputs

`public()` returns a `PublicSentinel`. The sentinel carries the public input name, default, display metadata, aliases, type hints, choices, and similar contract data. It is not itself a workflow input. It is a marker placed at a node kwarg use site, such as a prompt, seed, model name, or dimensions field.

`coerce_node_kwargs()` is the bridge between authoring syntax and workflow metadata. It walks node kwargs, replaces each `PublicSentinel` with its default value for the actual node input, and returns a `pending_publics` mapping keyed by kwarg name. Once `templates.node()` has created the node and knows the node id, it registers each pending public input on the workflow with `wf.register_input(...)`.

That two-step dance is necessary because the public-input declaration appears before the generated node id exists. It also explains why the bound `wf.node()` method now rejects pending publics: direct `wf.node()` does not have the higher-level template helper path that immediately registers the pending metadata after node creation. Raising there prevents a `public()` marker from being silently flattened into a plain default.

Filename-prefix kwargs are guarded separately. `coerce_node_kwargs()` rejects `InputSpec` and `PublicSentinel` values for filename fields because those fields are expected to remain concrete strings at authoring time.

## 5. Known Limitations

Helper/UI nodes (`Note`, `MarkdownNote`, `SetNode`, `GetNode`, `Reroute`) are not fully stripped by the generated Python emitter today. They may survive in generated Python when the emitter cannot resolve them away. Full helper stripping is a Family F Phase 1 TODO. The separate roundtrip caveat remains true: helper/UI nodes do not survive JSON -> Python -> JSON as first-class helper/UI nodes.

Ready-template line-1 markers are split into three recognized states:
`# vibecomfy: generated`, `# vibecomfy: manual`, and
`# vibecomfy: broken-regen`. Generated templates are eligible for automatic
regeneration. Manual templates are hand-owned and protected from overwrite.
Broken-regen templates are runtime-loadable shims whose build logic must stay
unchanged until Phase 1 fixes their source workflow families; they are also
protected from overwrite. The bulk converter and shared write gate refuse both
manual and broken-regen targets, while the load sweep verifies every checked-in
ready template has exactly one recognized marker on line 1.

Subgraphs and UUID-like runtime classes still need care. Some source workflows contain opaque or materialized subgraph structures where class ids, helper broadcasts, or schema validation issues cannot be reconstructed as clean first-class Python without additional source workflow context. Roundtrip tests tolerate documented UUID/subgraph and helper-strip caveats while still pinning class counts, edge shape, and public input keys for representative templates.

The AST contract extractor remains a legacy/fallback path. It should not be expanded casually to mirror every runtime feature. Generated-template contract truth should keep flowing through the runtime executor unless a template cannot load.
