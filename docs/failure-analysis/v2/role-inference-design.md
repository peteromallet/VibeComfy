# Confident role inference, uncertainty gating, and ambiguous role binding

## Purpose and current boundary

The provenance-evidence sliver should ship the specified **heuristics**: preserve every same-type source instance, describe its neighbourhood, attach a tentative role label, and use a cheap uncertainty trigger to decide whether to retrieve that evidence. It must not claim to solve semantic placement. M2 (“role-aware graph inspection + insertion planning”) and M4 (“typed candidate construction”) are where that claim can become defensible.

In this checkout, `research.py:_build_precedent_slices` is particularly lossy: it deduplicates workflow sources by `class_type`, loads a whole workflow, retains only node IDs/types and first/last anchors, and has no per-instance values, edges, roles, or confidence. `WorkflowSlice` and `PrecedentAdaptationPlan` in `executor/contracts.py` faithfully serialize that limited shape. The existing adaptation binder is also only a coarse baseline: `_anchor_roles` assigns substring-derived roles and `_build_anchor_bindings` takes the first target candidate with that role. That is exactly the behaviour m2 must replace, not embellish.

The requested `vibecomfy/executor/provenance.py` breadcrumb loader is not present in this working tree. The raw signal is nevertheless unambiguous: `porting/emit/ui.py` writes `extra.vibecomfy.source_template` and `extra.vibecomfy.prior_path`; `WorkflowNodeRecord`/`WorkflowLoadResult` from `ingest/workflow_source.py` can load and normalize source instances. M2 should introduce the missing executor-local breadcrumb-to-source resolver rather than imply that it already exists.

Here, **confident** means calibrated, evidence-backed, and abstention-capable. It never means “a plausible label produced more forcefully.” A confident label may make an insertion hypothesis or sibling splice eligible; it never authorizes copying source widgets. Values remain provenance-tagged ranked priors, subject to user intent, schema, topology, preservation conditions, and—where available—runtime evidence.

## 1. Confident role inference for custom or unknown nodes (D1)

The sliver’s neighbourhood label is useful orientation, but it cannot establish semantics. An opaque custom transform feeding a sampler can be a latent resize, a noise modifier, or a proprietary stage adapter; position and peer names alone do not decide which. The m2 brief is right to call custom-node inference research-bounded and expect medium confidence initially. The engineering to retain evidence and propagate uncertainty is not research-bounded; the semantic conclusion is.

M2 should define a graph-native `RoleEvidence` record for every relevant current and precedent instance, nested in an expanded `WorkflowSlice` (or a companion focused slice). It needs stable instance ID, class and pack/version provenance, schema-resolution status, named widget fields plus whether their names are authoritative, typed incoming/outgoing socket signatures, and incident edge endpoints including peer class and socket. It should also derive one- and two-hop upstream/downstream fingerprints; topological distance to inputs, outputs, samplers, encoders, decoders, and saves; branch membership; and sibling-equivalence groups. UI labels and canvas grouping can contribute weak context only. The record must contain an evidence ledger: every feature, source, and missing fact that influenced the label.

Infer from a bounded role vocabulary jointly with structural anchors, not from prose or arbitrary class names: for example `model_loader`, `conditioning_transform`, `base_sampler`, `refiner_sampler`, `latent_upscale`, `decode`, `terminal_output`, and `unknown`. Candidate roles come from compatible typed sockets and direction, consumer contracts, topology, authoritative schema descriptions/categories, pack metadata, and corroboration across known workflows. Widget values can distinguish otherwise similar stages, but are weak discriminators rather than a definition of role; otherwise role inference becomes a backdoor for golden-value copying.

Use an ensemble scorer with explicit probability mass for `unknown`, then calibrate it on human-labelled instance neighbourhoods split by template/workflow/pack—not a random node split that leaks duplicate graph structure across train and test. Report classwise precision and recall, reliability curves, and Brier score. Accept a role as **confident** only if (a) topology and schema/contract evidence exist, (b) the calibrated posterior meets a strict operating threshold, (c) it has a material margin over the next candidate, and (d) removing a weak feature or swapping an equivalent sibling does not change it. A high raw model score without those checks is not confidence.

Missing facts are negative evidence. Undocumented custom nodes, dynamic `INPUT_TYPES`, an unavailable pack, missing or stale schema, and a provenance path that cannot be loaded must lower the result and name the reason. Pack identity proves installation provenance, not semantic behaviour. An undocumented opaque node therefore remains medium or low confidence even when its graph location resembles a known node; there is no honest general solution without documentation, examples, or empirical execution evidence.

The fixer should receive candidates, calibrated probabilities/bands, the ledger, and missing/equivocal signals as an explicitly non-authoritative prior. Low confidence is `unknown` or multiple alternatives, never a single fabricated label. `executor/research.py` must extend source extraction and replace `_anchor_roles`/first-match `_build_anchor_bindings`; `contracts.py` must add immutable instance-role and candidate-binding fields; the new breadcrumb loader belongs beside this evidence path. `executor/core.py` and `comfy_nodes/agent/edit_research.py` must thread and render the uncertainty; because the current prompt emits a plan only when it is actionable, ambiguous `EditEvidence` needs its own neutral injection rather than being silently dropped. M4 then requires a confident compatible role/anchor *and* the relevant `EditIntent` path condition before sibling-clone/splice; repair feedback identifies the unsatisfied intent condition, never a source value to copy.

## 2. Reliable uncertainty detection for research gating (D2)

The sliver trigger—duplicate types, parallel branches, and role-specific settings—is a deliberate recall-oriented heuristic, not a reliable uncertainty detector. It over-researches when duplicate instances are semantically interchangeable, parallel branches are outside the requested path, or schema plus an explicit named target make placement forced. That wastes source lookup/search calls, latency, and model budget, and makes a simple edit look precedent-dependent. It under-researches when a graph has one instance of each type but several type-compatible insertion edges; when a custom node hides a stage distinction; when a user’s vague phrase names a semantic role rather than a node; or when non-default functional settings are necessary despite a linear topology. Under-research is worse: it supplies an apparently clean edit with no evidence to correct the wrong placement.

Do not make this a binary regex over graph shape. The improved m2 trigger should be a cheap deterministic **risk assessor**, used after graph inspection and before remote/corpus research. It first extracts the target capability and hard intent anchors from m1’s `EditIntent`; enumerates type-compatible insertion/bypass loci; detects active path and requested-branch coverage; and asks whether authoritative schema/defaults determine construction. It then scores independent uncertainty dimensions: intent ambiguity, placement multiplicity, role entropy from D1, branch-coverage ambiguity, value ambiguity, and evidence availability (a resolvable breadcrumb is cheap high-value evidence). A simple case proceeds without research only when the target, one placement, required coverage, and schema/defaults are all determined. Any high-risk dimension permits focused provenance lookup; remote similarity search is a second escalation only if the local source is absent or insufficient.

There is a useful cheap proxy before D1 is mature: count viable loci after type filtering, count demanded consumers/parallel paths, count same-class or same-signature siblings along those paths, and flag custom/unresolved schema plus high-impact unspecified values. It is intentionally conservative. It cannot know that two opaque nodes have different semantic roles, so it must record “role unknown” and escalate when the edit depends on choosing one. Mature D1 improves the trigger by replacing duplicate-type counts with calibrated role entropy; it does not eliminate the separate intent and coverage signals.

Measure the gate as a decision system, not by whether more demos pass. Build a labelled replay harness from real and synthetic workflows, with known intent conditions and both safe/no-research and evidence-needed edits. For each decision, record inputs, escalation tier, call count/latency/cost, candidate placement, and whether no-research would have violated an intent condition or needed information unavailable locally. Primary metric: **cost-weighted regret**—a missed-research error receives the cost of its incorrect/unsafe candidate or forced abstention; unnecessary research receives its measured cost. Also publish under-research rate at a fixed research budget, over-research rate on unambiguous edits, and calibration/reliability of risk bands. Hold out templates and custom-node packs to prevent provenance memorization. This is an engineering/evaluation problem once the labels exist; choosing semantics for underspecified user intent remains genuinely open.

Touch `ClassifyDecision` only to carry an auditable `research_risk` explanation/override, not a model assertion of certainty. The canonical route table in `core.py` currently hard-codes `revise` as no-research and `adapt` as research; it needs a risk-based prefetch decision that can attach focused evidence to a revise edit without silently redefining all edits as adapt. The batch REPL already marks research context discardable; preserve that boundary.

## 3. Binding a precedent instance to current anchors under ambiguity (D3)

“Same class” is not a binding key, and current first-candidate binding makes this concrete: a source anchor is paired with the first target node sharing a broad substring role. That is unsafe for two samplers, two `ManualSigmas`, or sibling resize nodes on divergent paths. The sliver’s correct degradation is to surface both labelled priors; m2 must make abstention an intentional result rather than an accidental absence of a binding.

For each source instance and each candidate current anchor, build a compatibility vector: class and typed socket compatibility; direction and slot-level incident-edge signatures; topology distances to shared anchor categories and terminals; upstream/downstream consumer role fingerprints; branch/path membership relative to the `EditIntent`; named explicit anchors in the request; schema-named non-sensitive configuration similarity; and source/current pack or model-family compatibility. Named user anchors and hard path/coverage conditions are constraints, not merely score features. Value similarity is only a low-weight tie-breaker after roles/topology match, never a reason to reproduce a source setting.

The binding algorithm is: (1) resolve source/current graphs and derive role distributions plus fingerprints; (2) discard pairs violating socket, explicit anchor, branch, or model-family hard constraints; (3) score the remaining bipartite pairs from calibrated role compatibility and structural similarity; (4) solve a global one-to-one (or declared one-to-many branch-coverage) assignment so greedy first-match choices cannot consume the wrong sibling; (5) run counterfactual checks—alternative near-optimal assignments, removal of weak value/UI features, and preservation/coverage validation. Bind only where the assignment is stable, clears a calibrated threshold, and has a sufficient margin over the best alternative. Return provenance, score components, alternatives, and the exact constraint that justified it.

It **must** stay “surface both” when candidates are structurally symmetric, posterior/margin is low, a needed schema/pack is unavailable, the user supplied no differentiating intent, or selecting either changes a high-impact value or destructive path. The system may ask a clarifying question or emit multiple placement hypotheses; it must not use source node ID, canvas position, or a benchmark value to break the tie. M4 may construct only from a confident binding; otherwise it can validate independent hypotheses but cannot clone/splice a presumed sibling.

This work replaces `research.py:_build_anchor_bindings` and expands its plan payload, with `WorkflowSlice`/`PrecedentAdaptationPlan` carrying alternatives rather than one winner. `core.py` must preserve the structured candidates across the executor boundary, and `edit_research.py` plus the batch repair path must expose them as priors. That satisfies m2’s “ranked with provenance, not dictated” decision and m4’s role-checked sibling-clone requirement without turning provenance into an answer key.
