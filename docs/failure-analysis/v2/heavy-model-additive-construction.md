# Heavy-model additive construction: cases 05 and 08

## Bottom line

The provenance sliver is working, but neither failure is now an evidence-availability problem. Case 05 first dies while publishing an otherwise locally accepted edit because the mutation-materialization digest rejects a legitimate boolean anywhere in an operation envelope. Case 08 does not reach the witness-bound oracle in the named rerun at all: the fixer applies three edits, continues from an incomplete construction, receives an empty provider response, and publishes no candidate. Its saved mid-session candidate also proves that construction would have failed the exact additive witness on topology, socket order, and widget ABI.

These cases can become green before m4, conditionally, through several general fixes in the current architecture. They will not become reliably green as a class until m4 supplies typed, atomic construction. The first pre-m4 change should be boolean-safe materialization canonicalization; the most important construction change is to make authoritative node schema—not provisional workflow inference—the sole authority for input order and emitted widget layout.

## Confirmed failure anatomy

### 05 — `WanVideoLoraSelect`

The live research result contains the expected source precedent and high-confidence tagged values: filename, numeric `strength: 1`, and boolean `low_mem_load: false` (`out/demo-candidate-factory/20260727-provenance-fixed/cases/e37d74df126b/attempts/001/research.json:5`). The source golden has one compact `WanVideoLoraSelect` node and one edge from its output to the surviving loader (`source/golden.ui.json:634`). The broken graph has neither.

The fixer did **not** turn strength into a boolean. Its actual batch emitted `widget_1=1.0` and `widget_2=False` (`out/editor_sessions/0719642fc95346d69192a9a97dd55cea/turns/0001/model_response.json:5`). The constructed candidate likewise holds numeric `1.0` followed by booleans (`.../candidate.ui.json:751`). The reported error, “Boolean is not a canonical numeric value,” is therefore not field-aware widget validation. It occurs after the edit gates pass, when `session.py` builds the mutation-materialization receipt (`vibecomfy/comfy_nodes/agent/session.py:4544`). `_accompanying_ops_digest` recursively canonicalizes the complete operation object without allowing JSON booleans (`vibecomfy/comfy_nodes/agent/mutation_materialization_v1.py:189`); the primitive canonicalizer then rejects a boolean as a numeric leaf (`vibecomfy/comfy_nodes/agent/_canonical_contract_primitives.py:144`). The projection path already passes `allow_bool=True` (`vibecomfy/comfy_nodes/agent/projection_registry_v1.py:708`), so this is an incomplete cross-contract rollout. The JavaScript mirror has the same defect (`vibecomfy/comfy_nodes/web/mutation_materialization_v1.js:131`).

There is a second construction failure behind the first. The candidate invented `WanVid/style_lora.safetensors` and materialized five widget values, whereas the golden UI node stores one compact filename widget. Its schema source was `workflow_json_provisional`, which also invented a required `prev_lora` input. Consequently, fixing boolean publication alone moves 05 from `fixer_failed` to likely oracle rejection. The retries then ask for filename and strength despite those priors already being present, demonstrating that visible priors are not reliably joined to the authoritative widget ABI.

### 08 — refinement sampler

The stated “oracle rejects the candidate” is not what the live artifacts record. The case status is `repair_failed` (`out/demo-candidate-factory/20260727-provenance-fixed/cases/789f795800b2/status.json:3`). Attempt 001 reports a provider error after “Applied 3 edits” (`.../attempts/001/implementation_result.json:3`), its response has `candidate: null`, `graph_unchanged: true`, and `apply_eligible: false`, and its only receipt is `executor_failure` (`.../receipts/001_repair_failed.json:2`). There is no evaluating receipt, proof, or case-level candidate. The pre-fix trace similarly times out without a candidate. Therefore no oracle witness actually failed in either named trace.

The closest saved editor candidate explains both the partial progress and the construction defect. The first batch adds two `WanVideoSampler` nodes and connects the second to decode (`out/editor_sessions/0cc9c5b330b44f2498f44f19f34f3137/turns/0001/model_response.json:16`; candidate nodes at `.../candidate.ui.json:859` and `:920`). Both take the model directly from node 22, bypassing the surviving block-swap node 70. Their provisional input order is model, text, image; the golden sampler order is model, image, text. The second sampler has eleven widget values, while the authoritative golden node has ten (`out/demo-candidate-factory/20260727-provenance-fixed/cases/789f795800b2/source/golden.ui.json:294`, widgets at `:347`). The fixer then tries to set provisional required fields to `None`, those edits fail, and the provider returns no continuation.

Had this candidate reached the oracle, it would fail legitimately. `_find_additive_witness` requires a node of the same type, all golden incident edges anchored to the same surviving peers and slots, and exact positional widget-list equality (`vibecomfy/demo_factory/predicates.py:32`). One added sampler is not connected to decode; the other has the wrong model peer, reversed image/text slots, an extra sampler chain, and a different widget vector.

The provenance record contains 28 tagged entries, representing 14 duplicated value priors (`.../attempts/001/research.json:2155`), but its selected slice contains no incident edges. `_incident_edges` only accepts mapping-shaped links (`vibecomfy/executor/provenance.py:191`), while LiteGraph UI links are six-element lists and normalization leaves them as lists (`vibecomfy/executor/provenance.py:137`). Thus the supposedly role-preserving source slice silently loses the topology most necessary for refinement placement. `WorkflowSlice` already supports incident edges (`vibecomfy/executor/contracts.py:850`); the loader is dropping them.

Change 1 is a type/materialization bug, but specifically **not** numeric-to-boolean coercion. A valid boolean is being fed to a canonicalizer configured for numeric-only leaves. Meanwhile, change 2 addresses the true widget-materialization smell: weak provisional inference shadows authoritative schema, so socket positions and raw widget vectors drift even when the model supplies correctly typed values. `_apply_add_node` orders inputs from the resolved schema and calls the UI materializer (`vibecomfy/porting/edit/apply_mutate.py:219`); a wrong provider therefore deterministically creates a wrong node.

Change 3 restores the part of provenance required for placement without turning priors into prescriptions. The sliver boundary analysis already warned that references and field-name authority were outside the value-only patch (`docs/failure-analysis/v2/provenance-sliver-boundaries.md:72`), while the role design says same class is not a binding key (`docs/failure-analysis/v2/role-inference-design.md:41`). The case 08 trace now supplies concrete proof that this boundary is active.

## Ordered recommendation and verdict

Implement 1 first because it is a localized correctness defect that prevents valid boolean-bearing edits from being published across many custom-node families. Then land 2 as one coherent schema/materialization correction, followed by 3. Add 4 before rerunning these cases so a remaining rejection identifies the first violated contract rather than producing another opaque retry. Do not “fix” provider exhaustion by publishing case 08’s last checkpoint: that checkpoint is incomplete and invalid.

The exact two cases can pass before m4, but only conditionally. For 05, changes 1 and 2 plus a retry that actually consumes the available filename evidence can produce the canonical node and edge. For 08, changes 2 and 3 can give the current fixer enough authoritative socket/widget structure and topology to construct the single missing sampler on the block-swapped path. That is a plausible regression green, not a reliable construction capability. Reliable success across WanVideo/LTX-wrapper additions genuinely requires m4’s typed atomic splice plus role-bound placement.

The anti-gaming line from `PLAN.md` remains firm (`docs/failure-analysis/v2/PLAN.md:69`): never auto-copy hidden golden values, hard-code WanVideo classes or filenames, weaken exact widget/edge predicates, or call serialization “execution.” Source-template values and edges are admissible evidence; the constructor must still select, type-check, bind, and validate them through the same public contracts used for any workflow.
