# Broad-view plan: VibeComfy additive editing

## 1. Product decision

VibeComfy should be built as a **real additive editor**, with the remove→restore demo retained as a subordinate regression suite rather than treated as the product specification. This is a staged verification strategy, not “finish the benchmark, then pivot”: the product path should accept any edit that satisfies an explicit validity contract, while a separate restoration track may require exact functional settings when the user asked to restore prior behavior and trustworthy provenance actually exists. That split changes all three boundaries. The real-editor oracle judges schema validity, role-correct topology, task postconditions, preservation, and—when available—runtime behavior; the restoration oracle may additionally compare against provenance. Research supplies patterns and constraints rather than an answer key. The agent must form and test a placement/value hypothesis, not copy a hidden node. The prior proposal is therefore right that evidence is being lost, but wrong to make exact provenance values the dominant product lever.

## 2. System map and load-bearing defects

Today the path is:

`campaign pairing/removal → classify → optional research → fixer/edit session → structural gates/port check → demo oracle`

- `demo_factory/run_campaign.py` pairs a ready template with a broad feature label. `creative.py` finds a node using category and type-name substrings, removes one node, and reconnects a bypass. `deltas.py` derives fault and repaired predicates from the hidden golden.
- `executor/core.py` asks the classifier to select a route. Route normalization makes `revise` mean implementation without research and `adapt` mean research plus implementation; contradictory booleans are canonicalized away.
- `executor/research.py` searches the local template corpus first, then Hivemind, registry/Manager/GitHub evidence, and web sources. It builds workflow slices and an adaptation plan. The implementation agent receives those plus the current graph and edits through the constrained batch/edit-session surface.
- The product edit path has substantial transaction and structural checks: stale-state protection, deterministic replay, IR/lowering, UI fidelity, schema/link validation, queue eligibility, and, for some precedent-backed complex edits, an `ExecutionPlan` semantic gate. The demo adds an offline `port check`.
- `demo_factory/oracle.py` calls that offline conversion result “execution safety,” checks that the fault predicate is gone and the repaired predicate is present, then checks non-no-op. Collateral-fence and narrative gates are stubs. For an additive node, `predicates.py` requires one node with the golden type, the golden incident edges anchored to surviving node IDs, and the golden positional `widgets_values`. Actual ComfyUI execution is not part of this oracle.

The ten cases reveal three system defects.

**1. There is no general task-success contract.** Classification chooses a process shape, but ordinary additive edits do not reliably produce machine-checkable obligations such as “upscale the input before it enters both edit consumers,” “apply this LoRA to every intended sampler model path,” or “add the second-stage sigma source, not another first-stage source.” The hidden golden currently substitutes for those semantics. Case 00 passes because type, insertion point, and defaults are all forced. Cases 01, 06, 08, and 09 show what happens as soon as duplicate node types, parallel branches, role-specific values, or stage placement make the edit underdetermined. Existing plan validation is the right seed, but it is scoped to selected precedent-driven routes rather than being the acceptance contract for additive work.

**2. Evidence is route-brittle and loses role.** A `revise` decision prevents research even when placement depends on workflow context (cases 06 and 09). The emitted graph already carries `prior_path` and `source_template` breadcrumbs, but they are not part of the classifier's compact graph view or a provenance-first research lookup. Conversely, research alone is not enough: cases 01, 05, and 08 found relevant or exact workflows, yet current workflow slices do not preserve the slot-level edges, per-node named values, target role, and all same-type instances needed for adaptation. The fixer then copied the first `ManualSigmas`, asked for a LoRA filename already present in a source, or emitted a provisional sampler layout. The missing abstraction is a focused, role-aware graph slice plus an adaptation hypothesis—not more search results.

**3. “Valid” is fragmented across fixture metadata, schema discovery, and verification.** Cases 02, 04, and 07 are invalid campaign pairings; they did not test the editor. Case 03 never reached it because schema resolution was opt-in and the IAMCCS pack was not routable despite source metadata containing its repository identity. Meanwhile the final oracle accepts offline conversion as execution and has no implemented collateral fence. Feature identity, pack/schema identity, graph roles, and oracle obligations need one typed capability layer; today each stage reconstructs a partial answer.

## 3. Validity versus exact identity

The product oracle should judge **validity**, not identity. It should evaluate a candidate against an `EditIntent` produced from the user request and current graph:

1. **Transaction and structural integrity (hard, always):** current baseline, deterministic replay, valid IR/lowering/UI round-trip, resolvable classes, named widget values within schema constraints, compatible socket types, required inputs satisfied, no dangling added component, and at least one intended output path preserved.
2. **Task postconditions (hard when high-confidence, otherwise reviewable):** required capability roles exist; the new component lies on the intended active path; all explicitly targeted branches are covered; ordering constraints are satisfied; and forbidden substitutions are absent. An upscale contract might specify the target image path and whether scaling is pre-encode or post-decode. A LoRA contract specifies which model path must be patched. These checks must be derived from the request and graph, not from golden node IDs.
3. **Role-correct settings (mixed):** explicit user values are hard constraints. Schema enums/ranges and model-family compatibility are hard constraints. Defaults, sibling settings, and precedent values are ranked priors with provenance and confidence, not universally required values. High-impact unresolved choices—model file, control mode, destructive resolution change—should either be surfaced for review or clarified; incidental values such as a new random seed should not fail identity comparison.
4. **Preservation/collateral fence (hard where provable):** diff only the intended causal region; preserve unrelated public inputs/outputs, branches, widgets, and canvas state. Start with graph slicing and touched-region rules; later add boundary-value or artifact checks.
5. **Runtime tier (strongest evidence, environment-dependent):** live queue validation, a bounded smoke execution, output collection, and feature-specific observations such as dimensions/frame count. Runtime success proves “runs,” not aesthetic quality. If models, custom nodes, or GPU are unavailable, return `structurally_valid_runtime_unverified` or `infra_blocked`, not a fictional execution pass.

The hard parts are semantic role inference for custom nodes, deciding intent when the request is underspecified, provisioning models/GPU, nondeterministic generative outputs, and judging qualitative improvement. A generic graph validator cannot prove that a four-value sigma schedule gives a good refinement pass. The oracle should report evidence levels rather than collapse all uncertainty into pass/fail.

Exact match remains appropriate for converter/serialization round trips, deterministic lowering, preservation tests, and the dedicated remove→restore regression when provenance is part of the scenario. Even there, compare canonical functional fields and topology—not canvas position or regenerated IDs. Exact golden settings must not define acceptance for novel edits.

## 4. Generalizable versus demo-shaped fixes

| Prior fix | Classification | Decision |
|---|---|---|
| `RestoreEvidence` packet | **Demo-shaped as proposed; generalizable when reshaped** | Replace it with `EditEvidence`: current-graph anchors and neighborhoods, all role-relevant same-type instances, schema with named fields, focused precedent slices, candidate placement hypotheses, and provenance/confidence per value. Add an exact-restoration section only when the user requested restoration and trusted history/source provenance exists. |
| Force research / bypass `revise` | **Generalizable policy if risk-based; demo-shaped if unconditional** | Do not force every additive request through research—case 00 proves that explicit type + forced splice + defaults needs none. Make research available when role, placement, capability, or functional values are uncertain, and let implementation request a focused slice after inspecting the graph. |
| Sibling clone/splice | **Generalizable product capability** | Keep as a typed candidate-building primitive: clone named fields from a role-compatible sibling and splice into a specific bypass edge with stable links. Never assume same class means same role; require an anchor/role check. Directly addresses case 06. |
| Re-pair campaign cases | **Test-fixture integrity only** | Keep. Validate feature presence and removability before scheduling. Source a real FaceDetailer workflow. Do not count newly runnable cases as passes. |
| Resolver environment/on-demand schemas | **Generalizable infrastructure plus fixture wiring** | Keep and broaden. Use safe read-only schema resolution consistently across research, authoring, baseline, and candidate checks; consume local pack provenance/overrides before remote discovery and record the source. Enabling an env var alone is only harness hygiene. |

## 5. Ordered roadmap

1. **Make `EditIntent` + validity evaluation the product contract.** Generalize the existing `ExecutionPlan`/plan-evaluation seam so every nontrivial additive edit can express anchors, required roles, ordering/path coverage, value constraints, preservation scope, and acceptable uncertainty. Split verdicts into structural, semantic, runtime, and provenance evidence; retain a separate exact-restore mode. **Why:** this replaces the hidden golden with an explicit definition of success and gives retries actionable failures. **Effort:** 1–2 weeks for the contract, evaluator shell, and several feature validators. **Confidence:** high on architecture, medium on first-pass role coverage. **Cases moved:** directly changes how structurally sound alternatives in 01 and 08 are judged and makes 09's wrong stage an explicit semantic failure; it supplies useful retry evidence for 05 and 06 but does not by itself make their edits land.

2. **Build role-aware graph inspection and insertion planning.** Label current nodes by observable role, enumerate type-compatible insertion/bypass points, detect parallel/sibling patterns, bind intended consumers, and rank placement hypotheses with evidence. Include “why here” and uncovered branches. **Why:** placement—not node lookup—is the central real-editor capability. **Effort:** 2–3 weeks. **Confidence:** medium; custom-node role inference needs iteration. **Cases moved:** 01, 06, 08, 09.

3. **Turn research into focused adaptation evidence.** Search summaries select candidates; then fetch one or two graph-native neighborhoods containing node IDs/types, named fields, edges, roles, and source provenance. Preserve every same-type instance and bind precedent roles to current-graph anchors. Treat values as constraints or priors according to source. **Why:** fixes evidence degradation without making a source template an answer key. **Effort:** 1–2 weeks. **Confidence:** medium-high because much of the slice/adaptation machinery already exists. **Cases moved:** 01, 05, 06, 08, 09.

4. **Harden typed candidate construction and the validate→repair loop.** Add schema-named constructors, sibling clone/splice, branch-coverage diagnostics, and retry feedback that points to the failed intent condition rather than a generic validation error. Eliminate provisional positional-widget guessing when an authoritative schema is available. **Why:** the agent often has the right idea but cannot land it. **Effort:** 1–2 weeks. **Confidence:** high for mechanical failures, medium for semantic selection. **Cases moved:** 05, 06, 08; supports 01 and 09.

5. **Unify schema and capability resolution.** Enable the same safe resolver ladder everywhere, index source-workflow pack metadata/local overrides, record resolution provenance, and distinguish schema-known from runtime-installed. **Why:** capability evidence should not change between baseline, research, and authoring. **Effort:** 3–5 days plus pack-specific tests. **Confidence:** high for removing the case-03 baseline block; unknown for its eventual edit. **Cases moved:** 03 and the metadata side of 02.

6. **Add runtime and artifact verification as an optional strong tier.** Integrate live queue/run/poll/output collection, use cheap parameters where supported, and add feature-specific observations before attempting perceptual quality judgments. Clearly separate missing assets from invalid edits. **Why:** static validity cannot prove shape compatibility or useful output. **Effort:** 2–4 weeks for a reliable first tier; behavioral comparisons remain research. **Confidence:** medium. **Cases moved:** 01, 03, 05, 08, 09 by producing evidence about whether plausible settings actually work.

7. **Split and rebuild the benchmark.** Keep an exact provenance-restore suite; add a novel-addition suite with no `prior_path`, multiple acceptable constructions, intent-based grading, negative placements, and runtime evidence where feasible. Preflight all workflow-feature pairings. **Why:** measurement must reward general capability and still catch preservation regressions. **Effort:** 3–5 days for suite structure, longer for quality scenarios. **Confidence:** high. **Cases moved:** 02, 04, and 07 become honest tests; no pass is claimed.

## 6. What not to build

- Do not inject hidden-golden node values into every fixer prompt and call the resulting score “additive editing.” That tests provenance plumbing, not placement or value reasoning.
- Do not hard-code these class names, node IDs, branches, LoRA filenames, sigma strings, or interpolation modes. They will improve this ten-case suite and fail on the next workflow.
- Do not broaden substring matchers merely to stop skips. ICLoRA may be a control mechanism, but equating every `iclora` node with a standard ControlNet silently changes the requested capability.
- Do not weaken exact widget checks in the existing suite without adding intent-based checks. That would admit case 09’s wrong pipeline stage as readily as a legitimate alternative.
- Do not call offline conversion or queue eligibility “execution,” and do not claim case 03 is solved when it merely reaches the agent.
- Do not mandate research for every add. It wastes the clean case-00 path and encourages precedent copying when local structure and schema already determine the answer.
- Do not optimize the campaign denominator: re-pairing three invalid cases creates three tests, not three capability wins.

## 7. Open questions for the human

1. **Restore semantics:** when trustworthy prior provenance exists, should “add it back” mean preserve prior functional values exactly, or may the agent substitute a valid modern equivalent? This decides whether exact-restore mode is a contract or only a diagnostic.
2. **Runtime bar:** can the product/CI assume a provisioned ComfyUI runtime with the required models and GPU, or must the default acceptance bar stop at structural/semantic validity with an explicit runtime-unverified state?
3. **Underspecified values:** should the agent autonomously choose high-impact settings and present confidence/provenance, or pause for user choice on items such as model files, control strength, and stage-specific schedules? This sets the boundary between useful autonomy and surprising behavior.
