### multi-svd-image-to-video-with-webp-and-png-output-bd3afb
- Judge verdict: FAIL (criteria: `correct_node_targeted=false`, `correct_parameter_changed=false`, `value_semantically_matches_intent=false`, `no_orphaned_wiring=true`)

No node, parameter, or connection was actually modified to make the PNG output save the first frame of the video, so C1–C3 fail; only the unchanged connected graph keeps C4 true."
- What the agent did: diagnosed the workflow correctly (TestLoader 13 → SVDSimpleImg2Vid 4 → fan-out to SaveAnimatedWEBP 9 and SaveImage 10; the static SaveImage receives the full video frame batch, not the first frame) and correctly proposed the canonical fix: insert `ImageFromBatch` (`batch_index=0, length=1`) between SVDSimpleImg2Vid and SaveImage. It verified `node_schema(ImageFromBatch)` → available (inputs `batch_index, image, length`; output `IMAGE`). It then attempted the edit **nine times across three turns**, all rejected:
  - **Turn 1 (seq 8, 26)** — reply-embedded DSL/statement path (no tool_call logged): `apply_rejected reason=unknown_source_name`: "Unknown graph name 'svdsimpleimg2vid' … Graph name 'imagefrombatch' is currently unbound because its add-node statement did not land. A later edit statement failed, so all edits from this batch were rolled back."
  - **Turn 5 (seq 33–71)** — typed `edit_batch` tool:
    - `inputs.image = {"source": "svdsimpleimg2vid", "output": "IMAGE_0"}` (dict ref form) → rejected: "no node in the current render resolves to "{'source': 'svdsimpleimg2vid', 'output': 'IMAGE_0'}"." (`unknown_target`, retryable).

  - **Turn 16 (seq 82, 98)** — fresh turn, fresh runtime: `add_node ImageFromBatch` with input `["svdsimpleimg2vid", "IMAGE_0"]` **resolved fine** (no error about svdsimpleimg2vid), but the chained `upsert_link(source="first_frame_extractor", …)` → rejected: "no node in the current render resolves to 'first_frame_extractor'." (`unknown_target`) — twice.
  - Final reply (r6 and r5 identical in substance): "I couldn't apply that change automatically in this session — both attempts to insert a first-frame extractor were rejected by the editor, so no graph change was accepted… add an ImageFromBatch node (batch_index 0, length 1) between SVDSimpleImg2Vid and SaveImage."
- Why it failed: the agent's diagnosis and intended Δ were **correct** — the judge's own rubric ("make the PNG output save the first frame of the generated video") is exactly what an ImageFromBatch insertion implements, and the graph-local wiring exists (philosophy #5: both endpoints present, same-class insertion). The edit never landed because the agent could not express a resolvable node reference:
  1. **Turn 1** went through the DSL/statement surface, which reported `svdsimpleimg2vid` as an unknown graph name — a name-resolution failure on the reply-embedded edit path (exact session state at that instant not fully recoverable from the log; see root cause).
  2. **Turn 5** invented reference syntaxes the typed resolver does not accept: a dict ref `{"source":…,"output":…}` and a `uid:`-prefixed ref (`uid:4`), instead of the binding name (`svdsimpleimg2vid`) or bare uid (`4`) that the lens/render exposes. The two-strike gate (`edit_tools.py:581-587`) then made the *third* (correct) attempt unreachable in that turn.
  3. **Turn 16** used the correct source binding for the add_node input, but referenced the **new node by the `name=` the agent chose** (`first_frame_extractor`) — and `name=` on add_node is only a *title* (`ops.py:190-191`), never a resolvable binding: bindings are a pure function of class_type (Law 5, `session.py:246-264`), so the new node's binding is `imagefrombatch`, not `first_frame_extractor`. The chained upsert_link could never resolve.
  - Contributing: `node_schema(SVDSimpleImg2Vid)` → "not available in the local/runtime schema providers" (custom class), and Hivemind research degraded (57014 statement timeouts), so the agent could not confirm slot/ref syntax externally.
- Class: **parse_or_tool_call_error** (guessed binding names / wrong reference syntax — `uid:4` prefix, dict-form source ref, title-as-binding ref; philosophy #9 "names over indices" violated by the model). Secondary harness contributions: the two-strike `second_rejection_no_candidate` gate makes the second bad guess terminal for the turn, and `add_node`'s `name=`→title-only contract is easy to misread as a binding. The judge is **not** wrong: no Δ landed.
- Root cause (code-level):
  - Model-side: `edit_batch` ops with non-resolvable refs. `resolve_target` (`vibecomfy/executor/edit_tools.py:262-290`) accepts only a binding name, a bare uid, or a numeric node id — it strips no `uid:` prefix and rejects the dict form as "no node in the current render resolves to {dict!r}". The add_node `name=` surface becomes `AddNodeOp.title` (`edit_tools.py:377-386`, `vibecomfy/porting/edit/ops.py:190-191`) and never enters `uid_by_name`, which is derived purely from class_type (`vibecomfy/porting/edit/session.py:246-264` via `emit_kwargs._compute_variable_names`, `vibecomfy/porting/emit/emit_kwargs.py:200-233`). Correct ref for the new node would have been `imagefrombatch`.
  - Harness-side: `vibecomfy/executor/edit_tools.py:581-587` — `if self._rejections >= 2: return second_rejection_no_candidate` hard-blocks all further edits in the turn, so the correct-form retry at seq 44/51/55/62/66/70 was never evaluated; `_reject` (`edit_tools.py:664-674`) counts semantic rejections, and `unknown_target` from `resolve_target` is classified semantic (`edit_tools.py:601-610`).
  - Turn-1 DSL path: `unknown_source_name` emitted from the statement interpreter (`vibecomfy/porting/edit/_interpret.py:1056`, `_resolve_name` at `_interpret.py:986-1028`; "add-node statement did not land" wording from `_interpret.py:996-1004`). Whether the turn-1 session's name map was empty (ingest state at that point) or fed a raw-graph name surface cannot be fully determined from the logged events — mark `unknown_needs_human` for that specific sub-path only; it is not needed to explain the judge verdict, since turns 5/16 alone prove the tool-call failure.

## Batch summary

Batch 5 is a single scenario, not six (r6's 25 failures partition as 6+6+6+6+1; the digest is authoritative and the "6" in the brief is template boilerplate). The dominant — and only — failure class is **parse_or_tool_call_error**: the agent held a correct, graph-local, judge-acceptable diagnosis (insert `ImageFromBatch(batch_index=0, length=1)` between SVDSimpleImg2Vid and SaveImage) but could not land it because every edit batch referenced nodes in syntaxes the resolver rejects — a dict-form source ref, a `uid:`-prefixed ref, and a fresh node referenced by its `name=` title (`first_frame_extractor`) instead of its class-derived binding (`imagefrombatch`) — while the harness's two-strike `second_rejection_no_candidate` gate made the second bad guess terminal for the turn, so the correct form was never even evaluated. The single highest-leverage fix is to make the edit surface self-correcting instead of terminal: (1) teach `resolve_target`/the prompt that add_node bindings are class-derived (`imagefrombatch`) and echo the **actual binding name of every newly added node in the tool result** (the runtime already computes `bindings` at `edit_tools.py:648-653` but never surfaces them to the model), and (2) on `unknown_target` from an unreachable ref, return a concrete "did you mean `svdsimpleimg2vid` / `imagefrombatch`?" correction as a *malformed-arguments* rejection (`_reject_args`, which does not consume the replacement window, `edit_tools.py:676-686`) rather than a semantic strike — turning a fatal guess-loop into a one-step recovery. Philosophy #9 ("names over indices") is satisfied only if the machine hands the agent the names it must use.
